# ResponseWatch 最终实施计划

[English version](ResponseWatch-plan.en.md)

- 项目：Health Systems / Emergency Response。
- 主要用户：911 急救调度中心当班主管。
- 团队：4 人，以 A、B、C、D 表示。
- 开发范围：可演示的 Web MVP，采用合成数据，不接入真实急救系统。
- 时间安排：沿用团队原计划，目标提交时间为 2026 年 10 月 17 日 12:30 ET，原计划列出的正式截止为 13:00 ET；提交前由团队核对赛事公告。

## 1 产品目标

帮助主管实时发现严重响应延误，识别被城市月均值掩盖的问题区域，查看延误发生在哪个环节，并登记排查和后续观察。

核心流程：实时事件记录 → 任务超时提醒 → 区域统计监控 → 具体任务与时间分段 → 跟进处理 → 后续观察。

工具回答四个问题：

1. 现在哪些任务即将超时、已经超时，或发生严重延误？
2. 哪些区域超过配置的服务目标，哪些区域相对自身历史出现异常恶化？
3. 延误集中在接警与派遣等待、出车准备，还是途中耗时？
4. 谁负责排查，正在采取什么行动，后续指标如何变化？

没有患者结局数据时，不把延误解释成死亡事件，不宣称降低了死亡率。时间分段用于定位调查方向，不能单独证明交通拥堵、车辆不足或人员失职。

## 3 页面与用户操作

### 3.1 实时指挥台

显示当前模拟时间、模式、任务列表、待派任务、已超时任务、严重延误和调度员当前任务量。提供查看详情、更新任务状态和确认提醒的操作。

本版记录调度员与响应车辆的分配信息，不建立个人绩效排名，也不声称具备自动选车或路线优化能力。

### 3.2 区域总览

每个区域展示任务量、平均值、中位数、P90、超时率、严重延误数量及两个独立标签：“超过服务目标”和“相对历史异常升高”。无样本显示“无数据”；样本不足时明确提示。

默认优先展示需要关注的区域，保留排序依据；不生成难以解释的综合风险分数。

### 3.3 区域与任务详情

区域详情展示每日 p 控制图、时间分段分布、最慢 5 个任务和跟进记录。任务详情展示已知时间戳、主要响应时间、总等待时间、超出目标的分钟数及备注。

### 3.4 跟进面板

跟进状态为待排查、处理中、待观察、已关闭。记录负责人、备注、创建和更新时间、关联任务或区域。已关闭仅表示管理记录完成，不代表统计上证明问题已解决。

原型可使用浏览器 localStorage，但须说明跨设备不共享、清除浏览器数据会丢失。按数据集或回放运行标识隔离记录；重置时清理或明确保留归档记录。

## 4 数据模型与时间口径

一行代表一个事件及其唯一响应车辆。合成数据统一使用一种高优先级，不处理多车辆响应、取消任务或优先级变更。

| 字段 | 用途 |
|---|---|
| `incident_id` | 唯一 ID，去重与更新 |
| `zone_id` | 现场所属区域 A–F |
| `priority` | 紧急等级，演示统一为 `high` |
| `call_received_at` | 接警时间 |
| `unit_notified_at` | 通知车辆时间，主要指标起点 |
| `unit_en_route_at` | 车辆出发时间 |
| `on_scene_at` | 到场时间，实时进行中允许暂缺 |
| `dispatcher_id` | 虚构调度员标识 |
| `unit_id` | 虚构响应车辆标识 |

所有时间戳采用带时区的 ISO 8601。以 America/New_York 的通知车辆日期归组，时间差输出分钟；跨午夜到场仍属于通知车辆日期批次。

```text
接警与派遣等待 = unit_notified_at − call_received_at
出车准备 = unit_en_route_at − unit_notified_at
途中耗时 = on_scene_at − unit_en_route_at
主要响应时间 R = on_scene_at − unit_notified_at
接警到场总等待 = on_scene_at − call_received_at
超出目标分钟数 = max(0, R − T)
```

主要服务阈值 T 默认为 12 分钟，超时定义为 R > T；等于阈值不超时。严重延误阈值 S 初始设为 24 分钟，严重延误定义为 R > S，且要求 S > T。T 和 S 都是演示配置，不是临床标准。

完整记录使用最终 R；进行中的任务使用“当前可见时间 − 通知车辆时间”计算已知等待。尚未通知车辆的任务只显示接警等待，不应用派车到场阈值。

校验必需字段、唯一 ID、区域、时区和时间顺序；禁止缺失值填零。历史 CSV 要求四个时间戳完整；实时状态由当前可见时间戳推导，不能提前录入后续状态。

车辆出发点与医院位置不作为 P0 必需字段。可在扩展中加入 `origin_zone_id`。未记录车辆释放时间时，不把已到场理解为车辆已可用，也不推断附近可用车辆数量。

## 5 三份合成数据

固定种子 5300，虚构城市六区，覆盖 2026-09-14 至 2026-10-11 共 28 天；每区每天 100 个任务，每份约 16,800 行。前 14 天为稳定基准期，后 14 天为监测期。

| 文件 | 规则 | 演示目标 |
|---|---|---|
| `normal.csv` | 稳定过程，带右侧长尾 | 展示正常波动与偶发极端任务，不保证零误报 |
| `hidden_tail.csv` | 第 18 天起，C 区约 25% 任务额外增加 6–12 分钟途中耗时 | 展示区域超时率、P90 和控制图信号变化 |
| `recovery.csv` | 复用恶化，第 24 天起移除额外延迟 | 展示模拟恢复后的观察，不作为真实干预效果证据 |

初始生成参数，单位为分钟：

| 分段或机制 | 配置 |
|---|---|
| 接警与派遣等待 | `clip(LogNormal(median=1.0, sigma=0.35), 0.2, 4.0)` |
| 出车准备 | `clip(LogNormal(median=1.2, sigma=0.25), 0.3, 4.0)` |
| 普通途中耗时 | `clip(LogNormal(median=6.0, sigma=0.25), 2.0, 10.0)` |
| 正常长尾 | 每事件以 10% 概率增加 `Uniform(6,12)` 途中耗时 |
| 额外恶化 | C 区指定期间以 25% 概率额外增加 `Uniform(6,12)` 途中耗时 |

常见库的对数正态均值参数使用 `log(median)`。正常长尾与额外恶化可以叠加。使用独立随机流生成掩码与增量，三场景复用相同底层抽样和基准期，避免无关区域随场景改变。

交付 `data/generate_data.py`、三份 CSV、`data/README.md` 和 `data/scenario_truth.json`。真值文件只用于测试和演示核对，统计模块不能读取场景名称或真值来决定异常。

另用精确小样本解释平均值的局限：10 个 8 分钟与 8 个 5 分钟加 2 个 20 分钟，均值均为 8 分钟，按 T=12 的超时率分别为 0% 与 20%。不宣称随机大数据集均值恰好相同。

## 6 统计与预警规则

统计集中在 `app/qc.py`，以纯函数实现；API 调用函数，前端不重复计算统计。

### 6.1 描述指标与极端任务

对完整有效记录计算样本数、均值、中位数、P90、超时数与比例、严重延误数及分段耗时。P90 使用线性插值：排序后 h=(n−1)×0.90，在相邻位置间插值。最慢列表按 R 降序，同值按 ID 排序。

明确区分完整记录的历史指标与进行中任务的计时。无样本返回无数据，不显示 0% 超时。小样本对 P90 显示不稳定提示，并公开提示规则。

### 6.2 p 控制图

按区域、优先级和通知车辆日期分层。基准 p0 为基准期超时总数除以有效总数，不平均每日比例。监测批次使用各自样本量：

```text
p_i = d_i / n_i
CL = p0
UCL_i = min(1, p0 + 3 × sqrt(p0 × (1−p0) / n_i))
LCL_i = max(0, p0 − 3 × sqrt(p0 × (1−p0) / n_i))
恶化信号：p_i > UCL_i
```

等于界限不触发；通过数值容差避免浮点边界误报，测试和文档使用同一约定。LCL 以下可提示改善信号，不证明干预有效。

假设基准稳定、同层事件近似独立且符合二项比例模型。当 p0 为 0 或 1、基准不足，或 n_i×p0 < 5、n_i×(1−p0) < 5 时，返回“控制图证据不足”，描述指标仍可展示。基准不足的明确规则须在实现前由 A/B 固定并记录。

只有已经结束且没有未完成任务的日期批次进入控制图。当前日期和含未完成任务的历史日期标记待结算。n=0 显示无数据。真实业务中的相关性、过度离散和多区域监测会影响误报，需另行校准。

### 6.3 三种独立状态

1. 当前任务超时：按实时等待与 T、S 判断。
2. 超过演示服务目标：完整批次超时率 p_i > q，q 初始为 10%，不等于统计显著。
3. 相对历史恶化：p_i > UCL_i。

保持独立标签，确保稳定但表现差的区域仍可见。T 调整后重新计算历史超时分类、p0 和控制界限；S 或 q 调整只影响相关严重延误或服务目标标签。保存阈值、基准期与配置版本。

## 7 历史模式与实时回放

历史模式允许查看完整数据。回放模式使用虚拟时钟，只显示该时刻可知的事件与时间戳，防止未来到场信息影响界面、排序或统计。

支持暂停、加速和重置，持续显示“合成数据模拟”、虚拟时间、数据集与配置。筛选监测日期不能悄悄重算冻结基准。

每个任务每个级别只产生一次提醒；一般超时可升级为严重延误。新提醒、已确认和已到场明确区分。确认只表示已查看；到场后停止活动计时，保留延误事实。切换场景与重置回放时隔离或清理提醒。

## 8 必须通过的验证

| 测试 | 预期 |
|---|---|
| p0=0.10，n=100，d=20 | CL=0.10，UCL=0.19，LCL=0.01，触发恶化 |
| 相同参数但 d=19 | 界限相等，不触发；覆盖浮点误差 |
| 8 个 5 加 2 个 20，T=12 | 均值 8，P90=20，超时率 20% |
| 基准两批 1/10 与 18/90 | 加权 p0=0.19 |
| 接警 12:00，通知 12:02，出发 12:04，到场 12:12 | 三段为 2、2、8；主要响应 10；总等待 12 分钟 |
| R=T、R=S 及略超阈值 | 严格大于规则一致 |
| 空数据、n=0、n=1、缺失、重复、逆序、无效时区、p0=0/1 | 明确状态或错误，无静默填零 |
| 跨午夜与未结算批次 | 通知日期归组正确，未结算不进入控制图 |
| 回放、重置、提醒确认 | 无未来泄漏、无轮询重复提醒、无跨场景混淆 |
| 改阈值与筛选日期 | 正确重算相关结果，日期筛选不改变基准 |
| 三场景与前后端一致性 | 生成可复现；核对实际检测批次；界面与统计函数一致 |

不要求每个恶化批次必然被检出；记录固定数据上实际检出的结果。极端任务列表即使在区域未越界时仍可展示。

## 9 架构与接口契约

沿用仓库约定，以 `demos/fastapi/` 为主要起点，采用 Python/FastAPI 与 React/Vite。保留 `testme`、`manifestme`、`deployme` 和 README 约定。React 构建产物由 FastAPI 提供，避免部署依赖两个独立开发服务器。

建议接口：`GET /health`、`POST /datasets/load`、`GET /incidents`、`POST /incidents`、`PATCH /incidents/{id}`、`GET /zones/summary`、`GET /zones/{id}/analysis`，以及回放控制接口。跟进可先本地存储，无需新增后端持久化。

首个 45 分钟固定样例请求与 JSON 返回结构，前后端使用模拟返回并行开发；统计验证通过后替换实现。接口返回单位、样本数、排除数、待结算数、筛选条件、阈值、基准期、配置版本及控制图可用状态。

实时约 2 秒轮询。事件保存在单进程内存时，界面说明重启重置；公开访客之间可能共享状态，使用已打包的合成演示数据，不接受敏感信息。CSV 在服务端校验并限制大小；重置操作不修改原始文件。
