## 1. 题目、用户与产品目标

**已选题目：Health Systems / Emergency Response。**

> Ambulance dispatch to on-scene times are varying wildly across city zones, but the 911 center only looks at monthly averages, missing fatal outliers, not where or why these failures occur. Design a statistical tool to help manage dispatchers, response time logging in real-time, generate analyzes, and flag zones that are in need of resolution.

主要用户为 **911 调度中心的当班主管**。核心工具帮助主管识别需要排查的区域、判断一天中哪些时段相对基准恶化、定位延迟环节，并比较正常、恶化和恢复场景。

本次必做主线：**载入场景或 CSV → 查看区域摘要及控制图 → 下钻延迟环节 → 解释异常与局限。** 输出表示响应延迟和统计信号；没有患者结局数据时，不把超时标记解释成死亡事件，也不宣称降低了死亡率。

按评审意见优先保证统计分析和可运行部署。新增单条事件、实时回放和调度跟进均为有门槛的可选项。若未实现实时功能，演示明确说明这是基于导入日志的统计监控原型，不宣称已接入真实 911 或完整覆盖实时调度。

## 3. 数据字段与时间口径

**一行代表一个事件及其唯一响应车辆。** MVP 的合成数据统一使用一种高优先级，暂不处理多车辆响应、取消事件或优先级变更。所有时间戳采用带时区的 ISO 8601；按 America/New_York 的通知车辆日期归组，时间差统一输出分钟。

| 字段 | 类型/示例 | 用途 |
|---|---|---|
| `incident_id` | 唯一字符串 | 去重和事件定位 |
| `zone_id` | `A`–`F` | 固定功能分区：A/B 市中心，C/D 住宅区，E/F 外围区 |
| `priority` | `high` | 按优先级筛选和配置目标 |
| `call_received_at` | 带时区时间戳 | 接警时间 |
| `unit_notified_at` | 带时区时间戳 | 通知车辆时间；主要响应指标的起点 |
| `unit_en_route_at` | 带时区时间戳 | 车辆出发时间 |
| `on_scene_at` | 带时区时间戳 | 到场时间；核心导入要求完整 |
| `dispatcher_id` | 虚构字符串 | 当前分配信息；不用于自动归责 |
| `unit_id` | 虚构字符串 | 唯一响应车辆标识 |

**时段为派生值，不新增用户必填字段。** 从 `unit_notified_at` 转换到 America/New_York 后得到时段；不使用接警或到场时刻分组。半开区间及基准切分见第 5.4 节。

区域类型同样由固定的 `zone_id` 配置派生，不增加调度员必填字段。真实接入时，优先从 CAD 已有响应辖区或地址的 GIS 映射取得区域，核对当地辖区/首响应站定义；不能假定所有系统已有相同边界。codebook 应说明当地字段或映射如何产生，而不是要求调度员手填功能区。

计算口径：

- 接警与派遣等待 = `unit_notified_at - call_received_at`。
- 出车准备 = `unit_en_route_at - unit_notified_at`。
- 途中耗时 = `on_scene_at - unit_en_route_at`。
- **主要响应时间 R = `on_scene_at - unit_notified_at` = 出车准备 + 途中耗时。**
- 接警到场总等待 = `on_scene_at - call_received_at`，作为另一个明确命名的描述指标。

主要服务阈值 **T = 12 分钟**，超时定义为 **R > T**；R 恰为 12 分钟不算超时。12 分钟为合成演示参数，不是临床或全国统一标准。阈值按优先级配置；调整阈值后，必须重新计算历史基准及所有超时指标。

核心导入只接受已经完成的历史记录，要求四个时间戳完整；校验唯一 ID、必需字段、合法区域、合法时区及时间顺序，不自动把缺失值填成零。可选的单条事件表单也先限定为完整记录。只有实际开展可选回放时，才增加未完成事件及当前可见状态模型。

## 4. 合成数据生成方案

**三份 CSV 均为虚构数据，固定随机种子 `5300`。** 不使用真实患者、真实调度员身份或外部交通数据。以虚构城市六个区域 A–F 为范围，覆盖 **2026-09-14 至 2026-10-11，共 28 天**；默认每区域每天 100 次事件，即每份约 **16,800 行**。

**采纳评审建议，保留每区每天 100 条。** 不主动减为 50 条：当 p0 约为 0.10 时，50 条刚好落在 n·p0=5 的近似适用边界，实际基准略低就可能不足。即使使用 100 条，也必须检查每区实际估计的 p0、`n_i*p0` 和 `n_i*(1-p0)`；未满足条件就返回证据不足。仅当文件大小确有问题时，再由 A/B 共同调整行数并重验。

前 14 天（09-14 至 09-27）为稳定基准期，后 14 天为监测期。三份场景复用相同基准和底层随机抽样，便于比较；基准期不会随新事件滚动重估。

| 文件 | 生成规则 | 预期演示 |
|---|---|---|
| `data/normal.csv` | 六区均采用稳定过程，响应时间为正且具有右侧长尾；出车准备与途中耗时分别生成 | 呈现正常波动；没有人为植入的恶化，不承诺随机样本绝无误报 |
| `data/hidden_tail.csv` | 从第 18 天起，仅对 C 区约 25% 的事件增加 6–12 分钟途中耗时；其他区域保留原始抽样 | C 区超时率和 P90 上升，部分批次触发控制图；城市平均值可能仍掩盖区域问题 |
| `data/recovery.csv` | 复用上述恶化；从第 24 天起移除 C 区额外延迟，保留一段恢复观察期 | 显示恶化及后续恢复，改善标记为模拟情景，不能当作真实干预效果证据 |

基础生成流程：先生成通知车辆时间与派遣信息，再生成正的出车准备及途中耗时，以求和方式得到到场时间；接警时间通过减去正的接警与派遣等待得到。普通与较慢事件可使用有上下界约束的对数正态混合分布。生成脚本中公开全部参数，调整后检查实际超时率及样本量是否适合预定统计方法。

以下参数作为可直接实现的初始配置，单位均为分钟；`clip` 表示截断到给定范围。对数正态的 median 是中位数，sigma 是对数尺度标准差：

| 参数 | 初始配置 |
|---|---|
| 接警与派遣等待 | `clip(LogNormal(median=1.0, sigma=0.35), 0.2, 4.0)` |
| 出车准备 | `clip(LogNormal(median=1.2, sigma=0.25), 0.3, 4.0)` |
| 普通途中耗时 | `clip(LogNormal(median=zone_median, sigma=0.25), 2.0, zone_cap)`，按下表取每区参数 |
| 正常长尾 | 每事件独立以 10% 概率增加 `Uniform(6,12)` 途中耗时 |
| 额外恶化 | C 区指定期间，每事件独立以 25% 概率额外增加 `Uniform(6,12)` 途中耗时 |

实现时使用 `log(median)` 作为常见库的对数正态均值参数，不把 median 直接当作对数均值。正常长尾和额外恶化可以叠加；提前用独立随机流生成恶化掩码和增量，避免切换场景改变其他区域的原始抽样。这些是演示生成假设，不能作为真实急救时长分布的经验结论。

### 4.1 固定的功能分区配置

| 区域 | 功能类型（虚构） | 普通途中耗时中位数 | 普通途中耗时上限 | 高峰倍数 |
|---|---|---:|---:|---:|
| A、B | 市中心 Downtown | 5 分钟 | 8 分钟 | 1.3 |
| C、D | 住宅区 Residential | 6 分钟 | 10 分钟 | 1.3 |
| E、F | 外围/半乡村 Outer / semi-rural | 7.5 分钟 | 12 分钟 | 1.3 |

六个 zone 保留固定功能身份；A 在 `data/generate_data.py` 中定义小型配置表，参数从基准期起生效，在 normal、hidden_tail、recovery 中一致。普通途中耗时统一 sigma=0.25、下限 2 分钟，其余按表取值。接警与派遣等待、出车准备继续使用共同分布，属于本次模型简化，不是现实中不受区域影响的结论。先统一使用 1.3 倍，不把 1.5/1.1 等候选值并入默认配置。

C 区恶化仍是第 18 天起全天独立 25% 概率额外增加 6–12 分钟，recovery 从第 24 天移除；不要把 E/F 原本较慢的基础特征当作植入异常。各区 p0 和各区各时段 p0_band 仍从实际生成的首 14 天独立估计、冻结，不能使用全市统一 p0，也不能从配置直接指定超时率。

提案的约 10%/12%/23% 来自另一组近似模拟条件，只作量级参考，不是本次已生成结果或验收常数。本计划小时权重下，高峰窗口权重为 8.4/25.6，约占 32.8%，并非该近似使用的约 25%。A 应在 codebook 记录固定种子实际生成的各区基准 n、超时数、p0、P90 及各时段样本；逐批检查 n·p0 和 n·(1−p0)，不能仅凭每区每天 100 条就保证适用。

### 4.2 小时分布与正常高峰

按通知车辆的本地小时加权抽样，再在该小时内抽取分钟和秒。每天每区仍固定 100 条；以下为**相对权重**，先除以总和 25.6 转成概率，不是每小时固定事件数：

| 本地小时 | 每小时权重 | 对应比较时段 |
|---|---:|---|
| 00–05 | 0.5 | 夜间 |
| 06、09 | 1.0 | 早高峰 |
| 07–08 | 1.5 | 早高峰 |
| 10–15 | 1.2 | 日间 |
| 16–19 | 1.8 | 晚高峰 |
| 20–23 | 0.8 | 晚间 |

在 **07:00–09:00、16:00–19:00** 的通知车辆时段，将普通途中耗时乘以 **1.3**；左闭右开。先截取普通途中耗时的上下界，再乘系数，最后加正常长尾和植入增量，避免重复放大增量。高峰系数窗口比第 5.4 节比较时段更窄，二者用途不同。

小时权重和正常高峰系数从基准期起就存在，并在三场景中一致，因此不作为人为植入的故障。A 必须在生成器与 codebook 中公开权重、系数、运算顺序、随机流和场景规则；A/B 在 H-02 开始前固定这些约定。

默认继续采用全天独立 25% 概率的 C 区额外延迟，保持每日主图的可检测性。提案中“仅在 16:00–20:00 集中植入”作为可选数据变体：只把原 25% 概率套在晚高峰会稀释全天效果，不能直接声称每日主图一定检测到。若采用该变体，A/B 必须记录调整后的注入规则、验证每日与时段两种视图的实际检测表现，并替换现有场景而非新增第四份 CSV；不因此推迟核心部署。

每区 14 天监测期仍有 1,400 条记录，但五时段不等量。按此权重，期望样本量约为 **夜间 164、早高峰 273、日间 394、晚高峰 394、晚间 175**；实际 n 由抽样决定。不能把各时段固定当作 280 条，仍需逐时段检查证据是否足够。

同时交付：

- `data/generate_data.py`：固定种子、参数和一条命令复现三份 CSV；将分阶段耗时转换成一致的时间戳。
- `data/README.md`：codebook，说明每列、单位、生成规则、限制，以及真实使用时需要从 CAD/EMS 日志取得哪些字段。
- `data/scenario_truth.json`：记录场景名称、种子、日期、受影响区域和植入规则，仅供测试与演示核对。**统计函数不读取此文件或场景名称来判断异常。**

“均值相同但长尾不同”使用独立的精确小样本测试说明：A 区为 10 个 8 分钟，B 区为 8 个 5 分钟加 2 个 20 分钟；两者均值均为 8 分钟，但按 T=12 计算超时率分别为 0% 与 20%。不预先声称随机生成的大数据集均值恰好相同。

数据验收：三份文件、每列说明、相同种子可复现、所有历史记录顺序合法、基准期一致、植入规则与实际场景吻合。样本不足及坏数据主要通过单元测试覆盖，不增加第四份演示 CSV。

## 5. 统计设计与限制

先实现并验证纯 Python 函数，再连接 API 和界面。所有统计集中在 `app/qc.py`，前端只负责展示。

### 5.1 描述指标

对有效、完整记录计算样本数、均值、超时数、超时率、P90 和分阶段耗时。超时率为 `d/n`。P90 固定使用线性插值：排序后令 `h=(n-1)*0.90`，在相邻的两个位置间插值；记录该定义，保证测试与界面一致。

**空数据与小样本：** n=0 时比例、均值和 P90 返回 null，界面显示“无数据”，不能显示 0% 或 0 分钟。n=1 时可显示该观测值作为描述性 P90，但提示样本不足。演示约定 n<20 时显示“小样本，P90 不稳定”；20 是界面提示规则，不代表达到 20 就能保证估计可靠。

**最慢事件为只读核心功能：** 从当前选定监测区间的完整有效记录取最慢 5 个，按主要响应时间 R 降序、同值按 `incident_id` 字符串字典序升序；少于 5 个就显示全部，空集返回 []。总览显示所选区域合计的列表，区域详情显示该区列表。每项展示 ID、区域、通知/到场时间、R 和 `minutes_over_target = max(0, R - T)`；所有值从现有字段派生，无新增必填输入。

该列表即使区域未触发每日控制图告警也必须可见，避免单次严重延迟被区域比例掩盖；未超时的慢事件仍显示超出分钟数为 0。它不引入实时计时、任务编辑或独立严重阈值 S=24。只读事件记录可通过现有摘要/详情接口返回，不增加第五个核心 API。

核心控制图采用**已经完整结算的通知车辆日期批次**，三份历史 CSV 的事件均已完成。若后续实现可选回放，必须单列进行中的事件及已知超时提醒；包含未完成事件的日期显示“待结算”，不能用已完成子集替代整批。虚拟时钟只暴露当前可见的时间戳，避免未来信息泄漏。这些实时状态要求不构成本次核心的实现前置条件。

### 5.2 p 控制图：识别近期恶化

按区域和优先级分层，每日为一个批次。用预先选定的稳定基准期估计该层的 `p0 = 基准期超时总数 / 基准期有效总数`，采用加权比例，不取每日比例的简单平均。每个监测批次使用自己的样本量 `n_i`：

```text
p_i = d_i / n_i
CL = p0
UCL_i = min(1, p0 + 3 * sqrt(p0 * (1 - p0) / n_i))
LCL_i = max(0, p0 - 3 * sqrt(p0 * (1 - p0) / n_i))
```

MVP 只启用一条恶化规则：**p_i > UCL_i**。等于界限不触发该规则；LCL 以下可提示改善信号，但不解释成已证明的改善。控制界限与分钟服务阈值 T 是不同概念。

模型假设：同一分层内事件近似独立、基准过程稳定、样本符合二项比例模型；普通 3σ 界限采用近似。MVP 对 `n_i*p0 < 5` 或 `n_i*(1-p0) < 5`、基准不足、`p0` 为 0 或 1 的情况显示“控制图证据不足”，不硬套公式判定正常。基准设定和相关性需人工检查；实际业务存在过度离散、共同拥堵或多区域同时监测时，需要重新校准告警，不能把单点越界当成因果证明。

**本次演示的基准充分性约定：** 每个区域/优先级使用固定 14 天基准窗；至少有 14 个非空、完整的日期批次，且基准中超时和未超时记录各至少 5 条。缺任一条件返回 `baseline_insufficient`，同时保留可计算的描述指标。每个监测批次仍执行上面的近似适用检查。数据充分不等于过程已证明稳定；合成基准的稳定性来自公开的生成假设，真实基准需人工审阅。

### 5.3 服务目标与解释

本轮核心演示启用允许超时率 **q = 10%**，与 T=12 一起显示为演示配置。完整批次/所选监测窗口的 `p > q` 显示“超过演示服务目标”，每日 `p_i > UCL_i` 另列“相对自身历史恶化”；两个标签独立显示，并标明各自日期范围。q 不是统计显著性或临床标准，证据不足不能伪装成无恶化。

预期故事是 E/F 因基础行车距离设定而长期较慢，可能持续超过 q，却通常没有持续偏离自身基准；C 在故障期相对自身基准恶化。实际比例和标记批次必须生成后核对，稳定区也可能偶然越界。“长期未达服务目标”只提示排查覆盖或服务目标适配，不直接证明车辆不足，也不因 E/F 相对稳定就称其服务合格。

分段图只说明延迟出现在哪个环节。途中耗时增加可提示检查覆盖范围、路线或交通证据；没有额外数据时不能直接断言拥堵、人员失职或车辆不足。P90 属于描述指标；小样本要标明不稳定。MVP 不强行加入 Cp/Cpk 或风险预测。

### 5.4 跨天汇总的时段比较：说明“何时”恶化

**每日“区域×天”p 图仍是主告警，公式及规则不变。** 在区域详情中增加第二个视图，由 `app/qc.py` 中新增的纯函数 `late_rate_by_band(df, T, baseline_end)` 计算。先完成并验证每日统计，再验证该函数，全部通过后 C 才显示对应图表。

从通知车辆的纽约本地时间派生以下五个半开区间：

| 键 | 显示名称 | 本地时段 |
|---|---|---|
| `night` | 夜间 | [00:00, 06:00) |
| `morning_rush` | 早高峰 | [06:00, 10:00) |
| `midday` | 日间 | [10:00, 16:00) |
| `evening_rush` | 晚高峰 | [16:00, 20:00) |
| `late_evening` | 晚间 | [20:00, 24:00) |

06:00 属于早高峰；10:00、16:00、20:00 分别归入后一个区间；次日 00:00 属于次日夜间。基准切分的排他性终点为 **`2026-09-28T00:00:00-04:00`**：之前为首 14 天，之后为第 15–28 天的监测期。

对每个区域、优先级和时段，将基准期及监测期分别**跨天汇总计数**。不制作“区域×时段×天”的额外控制图；100 条/天再分五组，很多点的 n·p0 会小于 5。比较的是整个监测期相对同一时段历史基准的变化，不是当前时刻风险预测。区域摘要表的主 flag 仍由每日图决定，时段 flag 只在详情中单列显示。

```text
p0_band = baseline_late_band / baseline_n_band  # weighted and frozen
n_band = total valid monitoring incidents in this zone and band
p_band = monitoring_late_band / n_band
pp = (baseline_late_band + monitoring_late_band) / (baseline_n_band + n_band)   # 合并比例
z_band = (p_band - p0_band) / sqrt(pp * (1 - pp) * (1 / n_band + 1 / baseline_n_band))
flag_band = z_band > 3        # 单侧、严格大于；用整数运算判定
UCL_band, LCL_band = 使 z_band = +3 与 -3 的 p_band 值（截断到 [0, 1]），
                     因此 flag_band 恰好等于 p_band > UCL_band
```

**H-11 修订（2026-10-16）：** 时段告警改为合并两比例 z 检验。旧版用 `p0_band + 3*sqrt(p0_band*(1-p0_band)/n_band)`，把 14 天基准比例当作精确值。每日图可以这样做（每天约 100 次呼叫，对比约 1,400 次基准呼叫），但时段的基准与监测样本量相近，基准自身的抽样误差与监测误差一样大。1,000 个模拟的正常月份中，旧规则有 57% 的月份至少出现一次时段误报；两比例检验为 3.7%，接近 30 个 3-sigma 比较的预期约 4%。三个数据集中所有植入的问题仍被标记。

基准无有效样本、监测 n=0、p0_band 为 0 或 1、`n_band*p0_band < 5` 或 `n_band*(1-p0_band) < 5` 时，返回“证据不足”，不除零、不标成正常，适用时保留描述性比例。界限为基于历史比例的近似比较界限，并非已进行多重校正的正式推断。

时段比较还要求所在区域/优先级先通过上述 14 天基准检查，且该时段基准中的超时与未超时记录各至少 5 条；不要求每个时段在每一天都有事件。未达标只抑制统计告警，不伪造 0% 或“正常”状态。

图表为五时段的基准/监测超时率并列柱，标出 UCL、样本量、比较日期及证据状态；越上界的时段用红色。返回数据放入现有 `GET /zones/{id}/analysis` 的 `time_of_day` 字段，无需新增接口或输入。每项至少返回 band、baseline_n、p0_band、n_band、p_band、ucl、lcl、flag、status。

UI 和 README 说明：**6 区×5 时段共 30 个探索性比较，偶然越界可能发生（无变化的月份中至少出现一次的概率约 4%，H-11），未做多重比较校正；红柱用于排查，不证明原因。** 同时段自身基准避免直接把正常高峰当成故障。恢复场景的汇总仍包含整个监测期内的故障日，因此“最后几天恢复”不保证整期时段红柱消失；近期恢复看每日主图。

风险调整的每日 p 图仅作通过 02:00 门槛后才可评估的统计扩展：每日预期超时数为 `E=sum(p0_band_of_each_call)`，计数界限为 `clip(E ± 3*sqrt(sum(p*(1-p))), 0, n_day)`。它处理时段构成变化，需另行测试和说明，不进入六项核心的验收，也不能阻塞部署。

## 11. 三个主要风险与应对

1. **统计口径错误：** 固定通知车辆到到场口径及历史基准；时段按纽约本地通知时刻派生并跨天汇总；A/B 交叉核算，明确 30 个探索性比较与近似假设。
2. **范围和部署拖延：** 只以六项 P0 为必做；回放、编辑、计时器和地图不阻塞部署；22:30 部署目标、02:00 可选资格门槛、11:00 冻结均明确执行。
3. **合成数据“自证正确”：** 公开参数与真值；统计模块不接触场景标签；用已知答案、独立小样本和边界测试验证，不仅依赖演示图。
