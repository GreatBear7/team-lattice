Overview

ResponseWatch helps an on-duty 911 dispatch supervisor identify where and when ambulance responses need attention. It separates performance against a service target from changes against each district’s own history.

Start with the district list, read the Response briefing, then inspect the supporting evidence. The briefing uses validated statistics and interpretation rules; it is not an external AI diagnosis.

All three demonstration datasets are fictional, completed incidents. This is a historical quality-review tool, not a live dispatch feed or an ambulance assignment system.
Open the dashboard →

Dashboard workflow

  1. Choose a dataset. Use one of the three built-in scenarios, or open API data → Upload completed incidents.
  2. Select a district. District overview shows its late-call rate and attention status. The selected district drives all supporting views.
  3. Read Response briefing. Its headline and large figure summarize the main evidence. Choose What changed?, What to check? or Limits, then follow the chart link.
  4. Investigate the evidence. Daily p chart shows unusual days; Where & when locates time-of-day changes; Why compares response stages.

Move horizontally across the daily plot to inspect the nearest date. Arrow keys also support daily inspection. Hovering over a date does not change the briefing’s analysis period.

Datasets and controls

Each dataset contains 16,800 incidents: six districts, 28 days and 100 calls per district per day. September 14–27, 2026 defines baseline; September 28–October 11 is monitoring. The generator seed is 5300.

Every dataset includes all six districts: A/B downtown, C/D residential, E/F outer or semi-rural. C and D name the planted changes, not the only districts included.

Time-of-day controls

Full period / latest seven days changes the hourly and time-band comparisons. District headline metrics and the daily chart retain the full monitoring period. 1h / 3h switches between raw hours and circular three-hour pooling in the heatmap and clock. These controls do not create additional statistical alarms.

Within targetAt most 10% of monitoring calls arrived late.

Not enough dataA comparison cannot be judged reliably. Missing evidence is not an all-clear.

What counts as late?

Response time runs from unit notification to arrival on scene. A call is late when this exceeds 12 minutes; exactly 12 is not late. The 10% target and 12-minute threshold are demonstration settings, not clinical standards.

“90% arrive within” is the response-time 90th percentile (P90). It describes the upper tail; it is not a control limit. Amber target failure and red evidence of change answer different questions.

Data and CSV uploads

Use a UTF-8 CSV of completed responses, up to 25 MiB. Each row represents one incident. IDs must be unique, districts A–F, and timestamps chronological with UTC offsets. Dates and hours are analyzed in America/New_York.

Required columnDefinition
incident_idUnique incident identifier
zone_idResponse district, A–F
call_received_atCall received
unit_notified_atUnit notified; response interval starts
unit_en_route_atUnit starts travelling
on_scene_atUnit arrives; response interval ends

Optional columns: priority, dispatcher_id, unit_id. If priority is present, only high-priority incidents enter analysis; otherwise all rows are assumed in scope.

Include the first 14 local calendar days for baseline and at least one later monitoring day. Insufficient comparisons remain unavailable. Invalid uploads report row, field and reason without replacing the active dataset.

Uploads are held in server memory and must be reloaded after a restart or expiry. No database setup is needed.

Methods and assumptions

Daily p chart: each district has its own frozen pooled baseline late rate. Three-standard-error limits vary with daily call count; a valid monitoring observation strictly above the upper limit is flagged.

Five-band comparison: a pooled two-proportion test accounts for uncertainty in both periods. An upper signal requires z > 3. The 30 district-band comparisons are exploratory and unadjusted.

Hourly heatmap and clock: colors show percentage-point changes, not independent hourly tests. Outlines reflect supplied pooled-band evidence.

Why / response stages: call handling, turnout and travel are compared descriptively using medians and P90s. Call handling precedes the response interval. Stage quantiles must not be added together.

Formulas, validity checks and worked examples

Formulas and worked examples

Every number on the dashboard comes from one tested file, app/qc.py. Worked examples below are its actual output.

1. Daily p chart (one per district)

Each day's calls are a pass/fail sample (late or not), so the late count is binomial. A p chart is the standard control chart for a proportion.

pi = latei / ni     p₀ = baseline late / baseline calls
UCL = min(1, p₀ + 3·√(p₀(1 − p₀)/ni))     LCL = max(0, p₀ − 3·√(p₀(1 − p₀)/ni))

A monitoring day is flagged when pi > UCL (exactly equal does not flag). Below the LCL means unusually few late calls, which is good news, so it is not flagged.

Worked example: Recovery, district C.

Baseline: 184 late of 1,400 calls → p₀ = 13.14%. Each day has n = 100.

3·√(0.1314 × 0.8686 / 100) = 3 × 0.0338 = 0.1014

UCL = 13.14% + 10.14% = 23.28%; LCL = 13.14% − 10.14% = 3.01%. Oct 1–6 are above 23.28% (up to 40%), so those six days are flagged; Oct 7–11 are back inside.

Limits for n = 100 calls a day. The baseline is identical in all three test datasets, so these limits are too.

Assumptions. Calls are roughly independent and the baseline is stable and representative. The tool checks n·p₀ ≥ 5 and n·(1 − p₀) ≥ 5 before drawing limits, and needs 14 baseline days with at least 5 late and 5 on-time calls. Real late calls can cluster (storms, busy hours), which would widen the true spread; a Laney p′ chart is the standard remedy and is not implemented.

2. Band test (pooled two-proportion z test)

For each district and time band, pool all monitoring days and compare with the same band's baseline. Both samples are a few hundred calls, so the test accounts for sampling error in both, not just the monitoring side.

p̂ = (latebase + latemon) / (nbase + nmon)
z = (pmon − pbase) / √( p̂(1 − p̂) · (1/nmon + 1/nbase) )

Flag when z > 3 (one-sided: only “worse” matters). The band's limit line is the monitoring rate at which z would equal exactly 3 for these sample sizes.

Worked example: Dataset 3, district D, 06:00–10:00.

Baseline 50 late of 280 = 17.86%. Monitoring 98 late of 264 = 37.12%.

p̂ = 148 / 544 = 0.2721    SE = √(0.2721 × 0.7279 × (1/264 + 1/280)) = 0.0382
z = (0.3712 − 0.1786) / 0.0382 = 5.05 > 3 → flagged

The equivalent limit is 28.71%. District D's other four bands have negative z.

Why not the p chart formula? Treating the band baseline as exact gave at least one false alarm in 57% of 1,000 simulated normal months. The pooled test brings that to 3.7%, close to the roughly 4% expected from 30 comparisons at z > 3.

3. Hourly heatmap and 24-hour clock (descriptive)

change (pp) = 100 × (pmon, hour − pbase, hour)

144 cells (6 districts × 24 hours), each with only about 20–130 calls, so cells are coloured but never tested. The 3h option pools each hour with its neighbours (23:00 wraps to 00:00). Black outlines come from the band test above.

Example: Dataset 3, district D, 08:00–09:00. Baseline 16.5% of 85 calls, monitoring 39.0% of 77 calls → +22.5 pp.

4. P90 (“90% arrive within”)

sort R; h = (n − 1) × 0.9; P90 = v[⌊h⌋] + (h − ⌊h⌋) × (v[⌊h⌋+1] − v[⌊h⌋])

Linear interpolation between the two nearest sorted values. Example: Dataset 2, district C has P90 = 17.6 min over the 14 monitoring days, so 1 call in 10 waited longer than 17.6 minutes. With T = 12 and q = 10%, P90 above 12 minutes goes with a late rate above 10%: P90 shows how far past target a district is. P90 is descriptive; it has no control limits.

5. Delay stages

call handling = notified − received
turnout = en route − notified
travel = on scene − en route (minutes)

Median and P90 of each stage, baseline vs monitoring. A stage whose P90 grows while its median barely moves points to a few very slow calls.

6. How we know the numbers are right

Known answers. p₀ = 0.10, n = 100 gives UCL 0.19 and LCL 0.01; 20 late calls flags, 19 does not. Band test: 120/600 vs 180/600 gives p̂ = 0.25, SE = 0.025, z = 4.0 (flag); a case with z exactly 3 does not flag.

Edge cases. No calls, all late, none late, too-short baseline, hour and band boundaries, and daylight-saving shifts all return an explicit status instead of a false all-clear.

Planted problems. Normal: no flags. Recovery: district C flagged Oct 1–6 plus two bands. Morning tail: district D morning band only. More than 200 automated tests check the statistics and the API.

Reference: D. C. Montgomery, Introduction to Statistical Quality Control, ch. 7 (control charts for attributes); the two-sample test for proportions in any applied statistics text.

Limitations

  • A signal prompts investigation; it does not prove a cause. The app does not attribute delays to individual staff or rank dispatchers.
  • No signal is not proof that service is acceptable. A district can be consistently above the target, and daily aggregation can hide a time-of-day change.
  • Statistical assumptions matter. Calls should be roughly independent and baseline performance representative. Clustering and changing demand can affect uncertainty.
  • Synthetic batch data only. No live CAD connection, real-time ingestion, incident editing or persistent uploaded-data storage is implemented.

Local setup and API essentials

Requires Python 3.12 and Node.js 20+ / npm. From a clone of the repository, run bash app/testme.sh, then open http://127.0.0.1:8000/. Run bash app/verifyme.sh for the verification suite.

Load a scenario or CSV with POST /api/datasets/load. Use the returned dataset ID with GET /api/zones/summary and GET /api/zones/{zone}/analysis. Rates are proportions, hourly changes are percentage points, durations are minutes, and missing values are null. Uploaded data requires one server worker in this version.

Statistical background: D. C. Montgomery, Introduction to Statistical Quality Control, control charts for attributes. Implementation details and known-answer checks are linked in the source repository.
